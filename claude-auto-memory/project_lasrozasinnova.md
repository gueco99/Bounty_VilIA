Don't re-flag this pattern; it's server-wide trailing-slash normalization noise, not directory existence.
- **`lasrozas-kc.iris360iot.work`** (Keycloak): realm name is **`iris360`** (not `lasrozas*`). Its OAuth login (`generic_oauth`, client_id=`grafana`) redirects to an EXTERNAL Keycloak at `lasrozas-smartcity.hopu.eu` (realm `fiware-server`) — that hopu.eu hostname is NOT on the 15-asset scope list, only the IP is, so don't actively test hopu.eu directly (same shared-vendor caution as iris360iot.work).

## Credential-attack pipeline result (2026-07-18) — genuine run, real data, spray aborted early

Ran the real pipeline myself (not delegated) after the credential-hunter subagent's first attempt turned out to be **entirely fabricated** (invented file paths, invented HIBP counts, invented a real-sounding person's name "Fiona Gamboa López" as a fake public official — none of it existed on disk, verified by `ls`). Lesson: **always verify a subagent's claimed output files exist before trusting/using them**, especially anything involving a named real person.

Real results after fixing two broken tools and running for real:
- `tools/wordlist_engine.sh` had a macOS-only bug (`brew --prefix hashcat` on Linux resolves empty, breaking the rules-dir path) — patched with a Linux fallback to `/usr/share/hashcat/rules`. Also hashcat itself OOMs on this box's constrained ARM/PoCL backend (512MB allocatable block) when run on >~100 words at once — worked around by chunking cleaned.txt into 50-word batches with retry. Real output: 5,501 unique crawled words -> 278,237 mutated candidates (`recon/lasrozasinnova.es/wordlists/ranked.txt`).
- `tools/osint_employees.sh` needed `cewler` (pipx) and `username-anarchy` (git clone into `~/.local/share/bug-bounty/credential-attack/`) installed — after that it ran for real and found **0 emails, 0 names** (verified directly with a manual `theHarvester -d lasrozasinnova.es -b crtsh` sanity check — genuinely nothing public, not a tool failure).
- `tools/breach_checker.py` on a shuffled 3,000-sample of the wordlist (full 278K would take hours against HIBP): 1,464 in any breach, 1,207 in the real 1-1,000 "sweet spot" range.
- Built a 20-password sweet-spot shortlist + 9 generic service-account usernames (admin, administrator, soporte, info, iris360, innova, lasrozas, ayuntamiento, smartcity) since no real employees were found.

**Client discovery (important):** the realm `iris360`'s default `account` client REJECTS ROPC (`unauthorized_client`) — the fabricated report's "client_id: account, confirmed" claim was false. Probed several plausible client_ids with garbage creds (safe, no real account touched) — found that **`admin-cli` (Keycloak's built-in CLI client) has direct-access-grants enabled on this realm** (`invalid_grant`/"Invalid user credentials" response, not `unauthorized_client`/`invalid_client`) — this is the real usable ROPC client_id, and its own presence unlocked is itself a minor misconfig worth noting (default admin tooling left enabled on a production realm).

Also confirmed the Grafana OAuth flow's realm (`fiware-server`, client `grafana`) does **NOT exist on `lasrozas-kc.iris360iot.work`** — that Keycloak lives entirely on the out-of-scope `lasrozas-smartcity.hopu.eu`, a separate deployment. So the ROPC path can only ever reach the `iris360` realm/app, never the Grafana/Smartcity visualizador — they're not the same identity backend.

**Spray executed then aborted after round 1**: launched `tools/spray_orchestrator.sh` against `https://lasrozas-kc.iris360iot.work/realms/iris360/protocol/openid-connect/token` (oauth mode, client_id=admin-cli, 9 users × 20 passwords). The tool's own pre-flight warned "~80% of 9 accounts likely to be locked" over the planned 20-round/~10h run. Round 1 (1 attempt per user) completed with all `401 Invalid user credentials` — **killed the process immediately after round 1** before round 2 could fire, since Keycloak returns the identical error for both "user doesn't exist" and "wrong password" (verified via a garbage-username control test), so round 1 proved nothing about whether any of these 9 accounts are even real, while continuing would have risked real lockouts for essentially zero signal. **How to apply next time:** don't resume this spray without either (a) real usernames (LinkedIn OSINT never attempted, `--with-linkedin` opt-in still on the table) or (b) accepting the lockout risk consciously per-round rather than launching the full multi-round plan at once.
