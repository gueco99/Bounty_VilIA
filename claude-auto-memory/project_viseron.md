Active since 2026-08-05. Secur0 VDP (program_id 134, scope_id 523 = github.com/roflcoopter/viseron), fresh target (0 prior reports before this session). Self-hosted, local-only NVR + AI computer vision (Python/Tornado backend, React frontend), Docker-deployed, "components" architecture (ffmpeg, mqtt, storage tiers, webserver, etc.).

Findings:
- **report_id 3611 (SUBMITTED)**: `viseron/components/webserver/__init__.py` calls `self._application.listen(DEFAULT_PORT, xheaders=True)` unconditionally — no check that the connection is actually behind a trusted reverse proxy. Combined with `check_rate_limit()` in `api/handlers.py` keying every rate limiter purely on `self.request.remote_ip`, this lets any client fully bypass the login (10/60s), token (30/60s), and onboarding (5/60s) rate limiters by rotating the `X-Forwarded-For` header per request — the ONLY brute-force defense in the app (no account lockout, no CAPTCHA). Verified live with real, unmodified `tornado.web` using the exact `xheaders=True` config (no viseron-specific mocking needed for this one — pure Tornado behavior). No live full Viseron instance available in this sandbox (needs opencv/torch/dlib/etc., impractical to stand up).
- **report_id 3652 (SUBMITTED)**: TOCTOU race condition in unauthenticated `POST /api/v1/onboarding`. `OnboardingAPIHandler.onboarding()` checks `self.auth.users or onboarding_complete` and only THEN calls `Auth.onboard_user()`/`add_user()`; `Auth._user_lock` only serializes same-username collisions inside `add_user`, never the outer open/closed decision. Two concurrent requests with different usernames can both pass the check while `users` is still empty, both proceed, and both become independent `Role.ADMIN` accounts — an attacker races the legitimate owner's first-run setup to plant a hidden admin account. Verified at 2 levels: (1) verbatim-copied `Auth` logic + handler flow with forced `threading.Barrier`s → both succeed; (2) real running `tornado.web.Application` with the exact async control flow (no server-side forcing) hit by 8 genuinely concurrent real HTTP POSTs (client-side barrier only) → 2 of 8 succeeded, creating 2 real admin accounts. CVSS `AV:N/AC:H/AT:P/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N`. Full working scripts (onboarding_race_test.py, real_http_server.py, race_client.py) importable/reusable as a general TOCTOU-onboarding-race test pattern for future targets with similar "first user wins" setup flows.
- **report_id 3680 (SUBMITTED)**: Broken access control on the WebSocket API. `subscribe_event`/`subscribe_states`/`get_entities` (`websocket_api/commands.py`) call straight into `Viseron.listen_event()`/`get_entities()` — primitives with literally no user/camera parameter in their signature — instead of the camera-scoped `connection.get_camera()`/`get_cameras()` accessor that the sibling command `subscribe_timespans` correctly uses. Any authenticated non-admin user, even one restricted via `assigned_cameras`, can subscribe to e.g. `"camera2/motion_detected"` or `"camera2/objects"` (simple, guessable camera-identifier-prefixed topic names) and receive live object-detection (labels+bboxes)/motion-detection/recorder-start-stop data for cameras outside their assignment — completely undermining the app's own per-camera privacy model (its whole reason to exist: sharing partial camera access, e.g. with a guest/family member). Full package import was impractical (heavy dependency chain — storage/camera/ffmpeg domains); verified via a standalone script replicating `DataStream.subscribe_data()`/`Viseron.listen_event()`'s exact verbatim signature/logic, showing zero-filter delivery. CVSS `AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:N/VA:N/SC:N/SI:N/SA:N`.
- **report_id 3682 (SUBMITTED)**: Same access-control bug class as 3680, but a separate endpoint/fix on the REST API. `POST /api/v1/events/amount` and `POST /api/v1/events/dates_of_interest` (`api/v1/events.py`) accept a `camera_identifiers` JSON list and pass it directly to `_events_amount()`/`_get_timespans_per_day()` (raw SQL `.in_(camera_identifiers)`) with ZERO ownership check — confirmed via grep that `_get_camera()` is called only twice in the file, both times in the sibling single-camera GET handlers (`get_events`/`get_events_amount`), never in either "multiple" POST handler. Leaks per-day motion/object/face-recognition/license-plate-recognition event counts + recording-timespan-availability booleans for any camera in the instance to any authenticated non-admin user, regardless of `assigned_cameras`. Lower severity than 3680 (aggregated counts, not raw labels/snapshot paths) — CVSS `AV:N/AC:L/AT:N/PR:L/UI:N/VC:L/VI:N/VA:N/SC:N/SI:N/SA:N`. Verified via a side-by-side replica script contrasting the safe single-camera path vs. the vulnerable multi-camera path against the same fake dataset.
- **General pattern learned this hunt**: viseron has a recurring anti-pattern where a camera-scoped single-ID code path correctly calls `_get_camera()`/`get_camera()`, but a sibling "multiple/bulk" or "raw event bus" variant skips it. Worth re-checking any other "accepts a list of camera_identifiers" or "operates on a raw topic/event name" endpoint not yet audited (e.g. any other bulk endpoints in `recordings.py`/`cameras.py`/`websocket_api` not yet reviewed) for the same gap.

Ruled out (investigated, not reportable — both required standing up a real, minimal Tornado harness to verify, not just code reading):
- `TieredFileHandler.handle_tier_hint()` (`viseron/components/storage/tier_handler.py` / `viseron/components/webserver/tiered_file_handler.py`) — takes attacker-controlled `first_tier_path`/`actual_tier_path` query params and does an unrestricted string-replace on a file path, producing a redirect. Looked like path traversal / cross-camera access bypass. Built a real Tornado test harness (avoided importing the real `viseron` package — its `__init__.py` eagerly drags in a huge, slow-to-compile ML/CV dependency chain — instead faithfully replicated the exact vulnerable code using only `tornado.web`). First pass (without the auth layer) appeared to show a real camera1→camera2 cross-access bypass (200 OK, real content). Re-tested WITH a faithful replica of the real per-request `assigned_cameras` auth check (`request_handler.py`'s `validate_camera_token()`, confirmed independently re-validates on every request including the redirected-to one) — bypass correctly blocked (401). Arbitrary-file-disclosure variant (redirecting outside any registered camera root) also fails — Tornado's own routing returns 404 since the crafted redirect target doesn't match any registered route pattern. Two independent layers (routing + per-request auth) both hold.
- `auth.py`/`api/v1/auth.py` — reviewed in full, genuinely well-hardened: timing-attack mitigation on login (fake bcrypt check + decoy JWT key), refresh-token rotation with reuse-detection grace period, session expiry enforced server-side (can't be extended via repeated refresh), PATs stored as SHA-256 hash only, admin-deletion/last-admin protections. No bypass found here directly (the XFF rate-limit bypass is a DIFFERENT layer, not a flaw in this module itself).

Corpus-informed hunting: the X-Forwarded-For rate-limit-bypass hypothesis came directly from grepping `memory/h1_technique_corpus/` for similar patterns (real Acronis HackerOne reports: "IP restriction bypass via X-Forwarded-For header", "Rate limit bypass...using X-Forwarded-For") — first practical payoff from the corpus-building work this session.
