Don't let "I reproduced this cleanly across N different commands/paths" read as evidence of security severity. Reproducibility quality and security impact are separate axes. A crash/bug triggered only by the local caller's own mistake (bad path, bad input), with no cross-user/cross-trust-boundary component, is a reliability bug — even when it's 100% reproducible and breaks a documented contract.

**Why:** On [[project_agentic_awesome_skills]], found and reported an unhandled-crash bug in the `aas` CLI — a missing/inaccessible local file path causes a raw native filesystem error to propagate uncaught, breaking the tool's own "always structured JSON" guarantee. Confirmed systemic (reproduced across 6 different subcommands, two distinct trigger conditions ENOENT/EACCES). Submitted honestly, with the trust-boundary caveat already written into the report. Vendor closed it same-day as "not a security vulnerability" — their reasoning: "triggered by the local caller supplying an invalid local path... does not cross a security boundary, access data belonging to another user, execute attacker-controlled code, or disclose information unavailable to the caller." Their call was fair, not a case of the vendor undervaluing a real issue — it matched the report's own honest framing.

**How to apply:** when a bug's only trigger is the same local user/process that would receive the impact (self-inflicted, no attacker-controlled input crossing into a different trust context), treat it as likely Informational/reliability regardless of how extensively it's been reproduced. Before spending more time strengthening the *evidence* of such a bug (more repro cases, more affected commands), spend that time instead checking whether there's an actual cross-boundary angle (can this be triggered by content/input an attacker controls against a victim, not just the user's own typo?) — that's the question that actually moves severity, not additional repro breadth. Complements [[feedback_no_informational_reports]] (the severity bar itself) — this memory is about not fooling yourself into thinking thorough reproduction substitutes for a real trust-boundary crossing.

**Second confirmed instance, a related-but-distinct shape (2026-07-31, [[project_boost_iosx]] #2822):** reported that `scripts/build.sh`'s marker-file early-exit (line 184) skips the Boost SHA256 check and all ICU/compile steps if two marker files already match, using whatever is in `frameworks/` as-is with no re-verification. Technically true and well-documented (real control-flow bug, false sense of integrity). Flagged myself, *before* triage, that the impact leaned on an unconfirmed precondition: the "attacker" needs prior write access to the build directory to plant tampered markers — but with that same access they could already overwrite `frameworks/` directly, achieving the same outcome without the bug at all. The only way it's a *real* escalation is a specific, unconfirmed CI topology (untrusted PR job sharing a persistent workspace with a later trusted release job) that the report itself hedged with "if" rather than confirming against the actual target's CI. Triage closed it same-day as Informative: "lacks sufficient impact... no realistic scenario in which an attacker could benefit... but worth fixing." Confirms the pattern generalizes beyond "local caller's own typo" — it also covers "attacker already has equivalent-or-greater access than the bug would grant." The tell in both cases: ask "what can the attacker do with this bug that they couldn't already do with the access the exploitation scenario assumes they have?" If the answer is "nothing new," it's Informational regardless of how solid the technical writeup is.
